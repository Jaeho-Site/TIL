# 타입 체크를 통과했는데 왜 런타임 에러가 나는가

[첫 글](/typescript/01-ts-js-relationship)에서 답을 미뤄둔 질문이 있다 — `names[2]`는 `undefined`인데 타입 체커는 왜 `string`이라고 믿었을까. 같은 종류의 코드를 책에서 다시 만났다.

```typescript
const xs = [0, 1, 2];
//    ^? const xs: number[]
const x = xs[3];
//    ^? const x: number
console.log(x.toFixed(1)); // 타입 에러 없음. 런타임: TypeError
```

`xs[3]`은 명백히 `undefined`인데 타입은 `number`다. `as`도 `any`도 안 썼다. 나는 컴파일러를 속인 적이 없는데 컴파일러가 스스로 틀렸다. 이런 일이 왜, 어디서 일어나는지 이번에 제대로 정리했다.

## 건전성이라는 이름의 약속

어떤 심벌의 정적 타입이 런타임에 실제로 나타날 수 있는 모든 값을 포함할 때, 그 타입 시스템은 **건전하다**(sound)고 말한다. [집합의 언어](/typescript/05-types-as-sets)로 쓰면 "런타임 값의 집합 ⊆ 정적 타입의 집합"이 항상 성립한다는 약속이다.

타입스크립트는 이 약속을 **의도적으로 완벽하게는 지키지 않는다.** 완벽히 지키려면 배열 접근마다 런타임 검사를 삽입하거나(타입이 지워지는 언어라 불가능하다), 개발자에게 훨씬 성가신 코드를 강요해야 한다. 자바스크립트 위에 얹히는 언어라는 정체성과 사용성을 위해, 몇 군데 구멍을 열어둔 것이다. 그래서 중요한 건 "구멍이 있다더라"가 아니라 **구멍의 위치를 아는 것**이다.

## 구멍의 지도

**1. any와 단언.** 앞의 [두](/typescript/10-any-unknown-never) [글](/typescript/11-type-assertions)에서 본 그대로다. 이 둘은 내가 명시적으로 여는 구멍이니 그나마 낫다. 진짜 무서운 건 아래의, 평범한 코드에 숨어 있는 것들이다.

**2. 배열과 인덱스 시그니처 접근.** 도입 퀴즈의 정체다. `number[]`의 인덱스 접근은 항상 `number`를 돌려준다 — 범위를 벗어났을 가능성은 무시된다. 객체의 인덱스 시그니처도 같다.

```typescript
type IdToName = { [id: string]: string };
const ids: IdToName = { '007': 'James Bond' };
const agent = ids['008']; // 런타임: undefined
//    ^? const agent: string
```

매 접근마다 `| undefined`를 붙이면 배열을 쓸 때마다 체크가 강제되어 너무 성가시다는 게 기본값의 논리다. 하지만 선택은 열려 있다 — `noUncheckedIndexedAccess` 옵션을 켜면 인덱스 접근이 `number | undefined`가 되고, 도입 퀴즈는 컴파일 에러가 된다. 대신 `for...of`나 `map`처럼 존재가 보장된 순회에는 원래부터 구멍이 없으니, 인덱스 접근 자체를 줄이는 게 먼저다.

**3. 함수에 넘긴 객체의 변경.** 별칭(alias) 문제라고도 부른다.

```typescript
function addFoxOrHen(animals: Animal[]) {
  animals.push(Math.random() > 0.5 ? new Fox() : new Hen());
}

const henhouse: Hen[] = [new Hen()];
addFoxOrHen(henhouse); // 통과 — 닭장에 여우가 들어갔다
```

`Hen[]`은 `Animal[]`에 할당 가능하다(읽기만 생각하면 자연스럽다). 그런데 함수가 배열에 **쓰기**를 하면, 같은 배열을 가리키는 `henhouse` 쪽 타입(`Hen[]`)이 거짓이 된다. 컴파일러는 함수가 인자를 변경하는지 추적하지 않는다. 방어법은 시그니처에서 의도를 못 박는 것 — 변경할 생각이 없다면 `readonly Animal[]`로 받으면 `push` 자체가 에러가 된다.

**4. 자식 클래스의 메서드 시그니처.**

```typescript
class Parent {
  foo(x: number | string) {}
}
class FooChild extends Parent {
  foo(x: number) { // 통과한다!
    console.log(x.toFixed());
  }
}
const p: Parent = new FooChild();
p.foo('string'); // 타입 에러 없음. 런타임 크래시
```

자식이 매개변수를 **좁혀서** 오버라이드했는데 컴파일러가 허용한다. 집합 논리로는 막아야 맞다(매개변수는 넓히는 방향만 안전하다). 하지만 메서드에 한해 타입스크립트는 양방향을 다 허용하는 느슨한 규칙을 쓴다 — 실용적인 타협이고, 대신 이런 크래시 가능성이 남는다. 참고로 메서드 문법(`foo(x: T)`) 대신 프로퍼티 문법(`foo: (x: T) => void`)으로 선언하면 엄격한 검사를 받는다.

**5. 부정확한 타입 정의.** `@types` 패키지나 손으로 쓴 `declare`가 현실과 다르면, 그 위의 모든 검사가 모래성이다. [두 번째 글](/typescript/02-runtime-types)의 `fetch` 응답 타입이 대표적인 사례였다 — 타입 선언은 희망 사항일 뿐 서버를 구속하지 못한다.

## 그래서 어떻게 지내야 하나

이 지도를 그리고 나서 개인적으로 내린 결론은 두 가지다. 하나, 타입 체크 통과는 "이 코드에 버그가 없다"가 아니라 **컴파일러가 아는 범위에서 모순이 없다**로 읽어야 한다. 테스트가 여전히 필요한 이유다. 둘, 구멍은 대부분 **경계**에서 열린다 — 인덱스 접근, 함수에 넘긴 가변 데이터, 외부에서 온 값, 상속 경계. 코드 리뷰에서 이 자리들만 의식해도 건전성 사고의 대부분을 미리 볼 수 있다.

---

타입스크립트의 타입은 보증서가 아니라 **정밀도 높은 지도**다 — 지도에 없는 낭떠러지가 몇 군데 있고, 그 위치는 언어가 공개적으로 문서화해 둔 트레이드오프다. 낭떠러지를 언어 탓하며 피해 다니는 것보다, 위치를 외워두고 `readonly`와 옵션으로 난간을 세우는 쪽이 생산적이었다.
