# 타입 체크를 통과했는데 왜 런타임 에러가 나는가

[첫 글](/typescript/01-ts-js-relationship)에서 답을 미뤄둔 질문이 있다 — `names[2]`는 `undefined`인데 타입 체커는 왜 `string`이라고 믿었을까. 같은 종류의 코드를 책에서 다시 만났다.

```typescript
const xs = [0, 1, 2];
//    ^? const xs: number[]
const x = xs[3];
//    ^? const x: number
console.log(x.toFixed(1)); // 타입 에러 없음. 런타임: TypeError
```

`xs[3]`은 명백히 `undefined`인데 타입은 `number`다. `as`도 `any`도 안 썼다. 나는 컴파일러를 속인 적이 없는데 컴파일러가 스스로 틀렸다. 이런 일이 왜, 어디서 일어나는지 이번에 제대로 정리했다.

## 건전성이라는 이름의 약속

어떤 심벌의 정적 타입이 런타임에 실제로 나타날 수 있는 모든 값을 포함할 때, 그 타입 시스템은 **건전하다**(sound)고 말한다. [집합의 언어](/typescript/05-types-as-sets)로 쓰면 "런타임 값의 집합 ⊆ 정적 타입의 집합"이 항상 성립한다는 약속이다.

타입스크립트는 이 약속을 **의도적으로 완벽하게는 지키지 않는다.** 완벽히 지키려면 배열 접근마다 런타임 검사를 삽입하거나(타입이 지워지는 언어라 불가능하다), 개발자에게 훨씬 성가신 코드를 강요해야 한다. 자바스크립트 위에 얹히는 언어라는 정체성과 사용성을 위해, 몇 군데 구멍을 열어둔 것이다. 그래서 중요한 건 "구멍이 있다더라"가 아니라 **구멍의 위치를 아는 것**이다.
