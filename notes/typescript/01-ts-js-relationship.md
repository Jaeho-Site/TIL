# 타입 에러가 있는데 왜 컴파일은 되는가

타입스크립트를 공부하기 시작하면서 제일 먼저 당황한 건 문법이 아니라 컴파일러의 태도였다. 책을 읽다가 만난 코드를 직접 `tsc`로 돌려봤다.

```typescript
let city = 'seoul';
console.log(city.toUppercase());
//               ~~~~~~~~~~~ Property 'toUppercase' does not exist on type
//                           'string'. Did you mean 'toUpperCase'?
```

오타를 잡아주는 것까지는 감동적이었다. 그런데 문제는 그다음이다. 이 상태에서 컴파일하면 결과물이 나올까?

나는 당연히 안 나온다고 생각했다. "컴파일 에러"가 났으니까. 그런데 폴더를 열어보니 멀쩡하게 변환된 파일이 있었다.

```javascript
// 에러가 났는데도 생성된 city.js
var city = 'seoul';
console.log(city.toUppercase());
```

에러를 뱉으면서 결과물은 내놓는 컴파일러라니. 처음엔 버그인 줄 알았는데, 사실 이게 타입스크립트라는 언어의 정체성을 그대로 보여주는 동작이었다.

## "컴파일 에러"라는 말이 오해를 만든다

내가 헷갈린 이유는 명확했다. C나 자바에서 컴파일 에러는 곧 "실행 파일 없음"이다. 그 감각으로 타입 에러를 봤으니 결과물이 없어야 정상이었다.

그런데 `tsc`는 이름만 컴파일러 하나이지, 실제로는 **서로 완전히 독립적인 두 가지 일**을 한다.

1. **타입 체크** — 코드가 타입 규칙에 맞는지 검사한다
2. **트랜스파일** — 타입 구문을 지우고, 필요하면 구버전 문법으로 바꿔 자바스크립트를 만든다

핵심은 2번이 1번의 결과를 **기다리지 않는다**는 것이다. 트랜스파일은 타입이 맞는지 볼 필요가 없다. `: string` 같은 타입 구문을 걷어내기만 하면 나머지는 이미 자바스크립트이기 때문이다. (`enum`이나 클래스의 파라미터 프로퍼티처럼 런타임 코드를 만들어내는 소수의 예외 문법도 있지만, 그것도 타입이 맞는지와는 무관하게 변환된다.) 그래서 타입 에러가 있어도 변환은 되고, 에러는 결과물 생성과 무관하게 보고된다.

이렇게 보면 타입 에러는 컴파일 에러라기보다 **아주 똑똑한 린트 경고**에 가깝다. ESLint가 경고를 띄워도 코드는 실행되는 것처럼, 타입 체커가 화를 내도 변환은 진행된다. 물론 이 동작이 싫으면 `noEmitOnError` 옵션으로 "에러가 있으면 결과물을 내지 마"라고 지시할 수 있다 — 기본값이 꺼져 있을 뿐이다.

## 왜 이렇게 설계했을까

타입스크립트는 **자바스크립트의 상위집합**(superset)이다. 확장자만 `.ts`로 바꾸면 모든 자바스크립트 파일은 그대로 유효한 타입스크립트다. 이 설계 덕분에 수십만 줄짜리 기존 JS 프로젝트를 한 번에 갈아엎지 않고 파일 하나씩 점진적으로 옮길 수 있었고, 타입스크립트가 지금의 위치에 온 결정적 이유가 됐다고 생각한다.

점진적 마이그레이션 중이라면 타입 에러는 사방에 널려 있다. 에러가 하나라도 있으면 빌드가 안 되는 언어였다면, 마이그레이션 중간 상태에서는 아무것도 실행해볼 수 없다. "에러는 알려주되 결과물은 준다"는 그 상황을 위한 선택이다.

다만 상위집합이라는 말을 "JS에서 되던 건 TS에서도 다 된다"로 읽으면 안 된다. 문법이 유효하다는 것과 타입 체커를 통과한다는 건 다른 얘기다.

```typescript
const a = null + 7; // JS에서는 7로 평가된다
//        ~~~~ The value 'null' cannot be used here.
alert('Hello', 'TypeScript'); // JS에서는 "Hello"가 뜬다
//             ~~~~~~~~~~~~ Expected 0-1 arguments, but got 2.
```

둘 다 자바스크립트에서는 합법이고 런타임 에러도 없다. 하지만 타입 체커는 막는다. 동작하는 코드라도 의도가 의심스러우면 잡아내는 것 — 이게 타입 체커가 하는 일이고, 문법 검사보다 한참 위에 있는 기준이다.

## 그럼 타입 체커를 통과하면 런타임 에러는 없는 걸까

이것도 궁금해서 찾아봤는데, 답은 "아니다"였다.

```typescript
const names = ['Alice', 'Bob'];
console.log(names[2].toUpperCase());
// 타입 에러 없음. 런타임: TypeError: Cannot read properties of undefined
```

`names[2]`는 `undefined`지만 타입 체커는 `string`이라고 믿는다. 타입스크립트의 타입 시스템은 런타임 동작을 **모델링**할 뿐, 완벽하게 보장하지는 않는다. 왜 이런 구멍이 남아 있는지는 그 자체로 파고들 주제라 뒤에서 따로 다룬다.

정리하면 타입스크립트가 그리는 지도는 이렇다. 모든 자바스크립트는 타입스크립트지만, 그중 타입 체커를 통과하는 코드는 일부다. 그리고 통과한 코드가 곧 에러 없는 코드인 것도 아니다.

## 타입이 지워진다는 것의 실무 쪽 결론

개인적으로 이 독립성을 이해하고 나니 실무 도구들의 구조가 한 번에 설명됐다. Vite가 대표적이다. Vite는 개발 서버에서 esbuild로 `.ts` 파일의 **타입만 지워서** 내보내고, 타입 체크는 아예 하지 않는다. 체크는 에디터의 언어 서비스나 `tsc --noEmit`(변환 없이 검사만)에 맡긴다. 타입 체크와 변환이 독립이라서 가능한 분업이고, 변환만 하는 esbuild가 tsc보다 압도적으로 빠른 이유이기도 하다.

그리고 타입이 전부 지워진다는 건, 타입을 아무리 정교하게 써도 **런타임 성능에는 영향이 없다**는 뜻이다. 타입은 개발할 때만 존재하는 층이다.
