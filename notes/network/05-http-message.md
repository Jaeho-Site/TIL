# HTTP 메시지는 어떻게 생겼나

[지난 글](/network/04-tcp-vs-udp)까지 데이터를 실어 나르는 전송 계층을 봤다. 이제 그 위에서 오가는 내용물 차례다. 터미널에서 `curl -v`로 요청 한 번을 떠보면, 브라우저가 매일 하는 대화를 날것으로 볼 수 있다.

```
> GET / HTTP/1.1
> Host: example.com
> User-Agent: curl/8.7.1
> Accept: */*
>
< HTTP/1.1 200 OK
< Date: Wed, 02 Sep 2026 12:30:48 GMT
< Content-Type: text/html
< Connection: keep-alive
< Age: 12155
< cf-cache-status: HIT
<
<!doctype html> ...
```

보기 전에 하나만 짚고 가자. 위 출력에서 **요청과 응답이 공유하는 구조**는 무엇일까? 사실 처음 이 출력을 봤을 때 나는 구조보다 다른 것에 놀랐다 — HTTP 메시지의 실체가 **그냥 몇 줄의 텍스트**라는 것. 개발자 도구에서 예쁘게 정리된 테이블로만 보다가 원문을 보니, 오히려 공통의 뼈대가 한눈에 들어왔다.

## 요청과 응답, 각각 세 부분

HTTP는 요청(request)과 응답(response)이 짝을 이루는 프로토콜이고, 두 메시지 모두 같은 뼈대를 가진다. **시작 줄, 헤더, (빈 줄 하나 건너) 본문.**

**요청 메시지**의 시작 줄은 `GET / HTTP/1.1` — 메서드, 경로, 프로토콜 버전이다. "무엇을(경로), 어떻게(메서드) 해달라"는 문장의 골격이다. 그 아래 헤더들은 요청의 부가 정보다.

- `Host`: 같은 IP의 서버 한 대가 여러 도메인을 서비스할 수 있어서, 어느 도메인에 온 요청인지 반드시 밝혀야 한다 (HTTP/1.1부터 필수 헤더다)
- `Accept`: 어떤 형식의 응답을 이해할 수 있는지
- `User-Agent`: 요청을 보내는 클라이언트의 정체

GET 요청은 보통 본문이 없다. POST라면 빈 줄 아래에 JSON 같은 본문이 붙고, `Content-Type` 헤더가 그 형식을 알려준다.

**응답 메시지**의 시작 줄은 `HTTP/1.1 200 OK` — 버전, 상태 코드, 상태 문구다. 요청의 결과를 숫자 하나로 요약한다. 헤더에는 응답 본문에 대한 설명(`Content-Type`, `Content-Length`)과 연결·캐시에 대한 지시가 실리고, 빈 줄 아래에 실제 내용물 — HTML, JSON, 이미지 바이트 — 이 온다.

`fetch` 코드와 겹쳐 보면 이 구조가 그대로 API에 반영되어 있다.

```javascript
const res = await fetch('/api/posts', {
  method: 'POST',                                  // 시작 줄의 메서드
  headers: { 'Content-Type': 'application/json' }, // 헤더
  body: JSON.stringify({ title: '...' }),          // 빈 줄 아래 본문
});
res.status;      // 응답 시작 줄의 상태 코드
res.headers;     // 응답 헤더
await res.json(); // 응답 본문
```

fetch의 옵션 객체는 사실 HTTP 요청 메시지의 구조를 자바스크립트 문법으로 옮겨 적은 것에 가깝다.

## HTTP는 왜 상대를 기억하지 않나

메시지 구조보다 더 중요한 건 이 프로토콜의 설계 철학이다. HTTP는 **무상태**(stateless)다. 서버는 요청 하나를 처리하고 나면 그 요청에 대한 어떤 것도 기억할 의무가 없다. 방금 나와 대화한 서버가, 다음 요청에서는 나를 처음 보는 것처럼 대한다.

처음엔 이게 결함처럼 보였다. 로그인은? 장바구니는? 하지만 [UDP에서 봤던 것](/network/04-tcp-vs-udp)과 같은 구도다 — **비어 있음은 의도된 여백이다.** 서버가 클라이언트마다 상태를 기억해야 한다면, 모든 요청은 "그 상태를 기억하는 특정 서버"로만 가야 한다. 기억하지 않기 때문에 어떤 요청이든 아무 서버나 처리할 수 있고, 서버를 100대로 늘리는 수평 확장이 가능해진다. 웹이 지구 규모로 커질 수 있었던 바탕이다.

물론 로그인 상태 유지가 실제로 필요하고, 무상태 원칙 위에서 상태를 얹는 별도의 장치(쿠키)가 존재한다 — 이건 [따로 한 편](/network/08-cookie-session)으로 다룬다.

## 비연결성, 그리고 keep-alive라는 절충

초기 HTTP(1.0)는 무상태에 더해 **비연결**(connectionless)이기도 했다. 요청 하나 처리하면 TCP 연결을 즉시 끊었다. 그런데 [연결 수립의 비용](/network/02-tcp-handshake)을 이미 봤다 — 요청마다 3-way 핸드셰이크를 다시 하는 건 낭비가 너무 컸다. 웹 페이지 하나가 수십 개의 리소스를 요구하는 시대엔 더더욱.

그래서 HTTP/1.1은 **지속 연결**(persistent connection)을 기본값으로 바꿨다. 위 curl 응답의 `Connection: keep-alive`가 그 흔적이다 — "이 연결, 끊지 말고 다음 요청에 재사용하자"는 뜻이다. 무상태라는 철학은 유지하되(서버는 여전히 나를 기억하지 않는다), 연결이라는 물리적 자원은 재사용하는 절충이다. 상태와 연결이 별개의 개념이라는 게 이 지점에서 분명해진다.

## 헤더를 읽을 줄 알면 디버깅이 달라진다

개인적으로 HTTP 메시지 구조를 익히고 가장 체감한 변화는 개발자 도구를 읽는 눈이었다. Network 탭에서 요청을 클릭했을 때 보이는 Headers 패널이 곧 위의 날것 메시지다. API가 이상하게 동작할 때 "요청에 `Content-Type`이 제대로 실렸나", "응답의 상태 코드가 정말 200인가, 200인데 본문이 에러인가"를 먼저 확인하는 습관은 여기서 나온다. 프론트엔드와 백엔드 사이의 논쟁 대부분은 이 메시지 원문을 같이 보는 순간 끝난다.

HTTP 메시지는 시작 줄·헤더·본문으로 이루어진 텍스트 기반의 대화이고, 서버가 상대를 기억하지 않는 무상태 설계 덕분에 웹은 수평으로 확장될 수 있었다.
