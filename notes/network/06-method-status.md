# GET으로 삭제하면 왜 안 되나

공부하다가 이런 API를 만났다고 하자. 실제로 오래된 코드에서 종종 발견되는 형태다.

```
GET /api/posts/42/delete    → 글 42번 삭제
```

동작은 한다. URL을 호출하면 글이 지워진다. 그런데 이 설계에는 시한폭탄이 들어 있다. **서버를 공격하는 사람이 없어도 글이 무더기로 사라질 수 있다.** 누가 지우는 걸까?

답은 크롤러와 프리페처다. 검색 엔진 봇이나 링크 미리보기 봇은 페이지의 링크를 자유롭게 따라다니며 GET 요청을 날리고, 브라우저의 프리페치는 한술 더 떠 **내 로그인 세션을 실은 채로** 링크를 미리 밟는다. 봇이 이 링크를 밟는 순간 글이 지워진다. 봇이 잘못했나? 아니다 — **GET은 몇 번을 호출해도 서버 상태가 변하지 않는다는 약속**을 믿었을 뿐이다. 약속을 어긴 건 API 쪽이다.

## 메서드는 CRUD 매핑이 아니라 약속이다

처음에 나는 HTTP 메서드를 데이터베이스 CRUD의 매핑 정도로 이해했다. GET=SELECT, POST=INSERT, PUT=UPDATE, DELETE=DELETE. 틀린 건 아니지만, 이 프레임으로는 위의 사고를 설명할 수 없다. 메서드의 진짜 의미는 두 가지 성질로 정의된다.

**안전성(safe)**: 호출해도 서버의 상태가 변하지 않는가. GET과 HEAD가 안전하다(OPTIONS도 안전한데, 이 녀석은 [CORS 편](/network/11-sop-cors)에서 다시 만난다). 크롤러가 수백만 개의 URL을 겁 없이 호출할 수 있는 근거, 브라우저가 페이지를 미리 가져와도(prefetch) 되는 근거가 전부 이 성질이다.

**멱등성(idempotent)**: 같은 요청을 한 번 보내든 열 번 보내든 서버의 최종 상태가 같은가. 이게 중요한 이유는 네트워크의 현실 때문이다 — 요청을 보냈는데 타임아웃이 났다면, 요청이 서버에 안 닿은 건지 **처리됐는데 응답만 유실된 건지 클라이언트는 알 수 없다.** 멱등한 메서드라면 고민 없이 재시도하면 된다. 멱등하지 않다면, 재시도가 곧 중복 처리다.

| 메서드 | 안전 | 멱등 | 의미 |
|---|---|---|---|
| GET, HEAD | ✅ | ✅ | 조회 — 캐싱과 자동 재시도에 적합 |
| PUT | ❌ | ✅ | 전체 교체 — 열 번 덮어써도 결과는 같다 |
| DELETE | ❌ | ✅ | 삭제 — 이미 지워진 걸 또 지워도 "없음"은 같다 |
| POST | ❌ | ❌ | 생성·범용 — 반복하면 중복 생성된다 |
| PATCH | ❌ | ❌ | 부분 수정 — 명세상 멱등을 보장하지 않는다 |

이 표가 실무 판단으로 이어지는 대표 사례가 결제다. 결제 요청은 POST인데 멱등하지 않으므로, 재시도 로직이 무심코 들어가면 중복 결제가 된다. 프론트엔드에서 결제 버튼에 디바운스·비활성화 처리를 하는 건 UX 문제이기 전에 **멱등성 없는 메서드에 대한 방어**다.

PUT과 PATCH의 구분도 이 관점으로 정리된다. PUT은 리소스 전체를 보내 통째로 교체하므로 몇 번을 반복해도 결과가 같다(멱등). PATCH는 변경분만 보내는데, `{"name": "Jaeho"}`처럼 값을 덮어쓰는 형태면 사실상 멱등하게 동작하지만, "카운터를 1 올려라" 같은 연산형이면 반복할수록 결과가 누적된다. 그래서 명세는 PATCH의 멱등성을 보장하지 않는다.
