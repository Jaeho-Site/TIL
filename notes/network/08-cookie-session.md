# 무상태인데 로그인은 어떻게 유지되나

[HTTP 메시지 편](/network/05-http-message)에서 서버는 요청이 끝나면 나를 기억하지 않는다고 했다. 그런데 현실의 나는 아침에 로그인한 사이트를 저녁까지 잘 쓰고 있다. 공부하다 이 지점을 파면서 스스로 문제를 하나 만들어봤다.

> 로그인 성공 직후, 서버가 보낸 응답 헤더에는 무엇이 들어 있을까? 그리고 그다음 요청부터 브라우저가 하는 일은?

핵심은 **기억의 주체를 바꾸는 것**이다. 서버가 나를 기억하는 게 아니라, **내가 서버에게 나를 증명할 것을 매번 들고 다닌다.**

## 쿠키 — 매 요청에 따라붙는 메모

로그인 성공 응답에는 이런 헤더가 실려 온다.

```
HTTP/1.1 200 OK
Set-Cookie: sessionId=abc123; Path=/; HttpOnly; Secure; SameSite=Lax
```

브라우저는 `Set-Cookie`를 받으면 그 값을 저장해 두고, **같은 사이트로 가는 모든 후속 요청에 자동으로 붙인다.**

```
GET /mypage HTTP/1.1
Cookie: sessionId=abc123
```

이게 쿠키의 전부다 — 서버가 "다음에 올 때 이 쪽지를 보여달라"고 건네준 메모를, 브라우저가 성실하게 매번 제시하는 것. HTTP 자체는 여전히 무상태다. 프로토콜을 고친 게 아니라, **헤더 위에 상태를 얹는 관례**를 만든 것이다.

## 그런데 쿠키에는 무엇을 담나 — 세션 vs 토큰

쿠키는 운반 수단일 뿐이고, 진짜 설계 질문은 **그 안에 무엇을 담을 것인가**다. 두 갈래가 있다.

**세션 방식 — 서버가 기억하고, 쿠키엔 열쇠만.** 서버는 로그인 시 세션 저장소(메모리, Redis 등)에 "abc123 = 사용자 42번, 로그인 시각 …"을 기록하고, 쿠키에는 그 열쇠인 세션 ID만 담아 보낸다. 실제 정보는 전부 서버에 있으므로 클라이언트가 위조할 수 없고, 서버에서 세션을 지우는 순간 즉시 로그아웃시킬 수 있다. 대신 [무상태 덕분에 가능했던 수평 확장](/network/05-http-message)에 숙제가 생긴다 — 서버가 10대라면 세션 저장소를 공유하거나 같은 사용자를 같은 서버로 보내는 장치가 필요하다.

**토큰 방식 — 정보를 서명해서 클라이언트에게.** JWT가 대표적이다. 서버는 "사용자 42번, 만료 시각 …"이라는 정보 자체에 서명을 붙여 토큰으로 만들어 클라이언트에 준다. 이후 요청에서 서버는 저장소를 뒤질 필요 없이 **서명만 검증하면 된다.** 상태를 다시 클라이언트 쪽으로 밀어낸 것이라 수평 확장과 잘 맞는다. 대신 이미 발급된 토큰을 서버가 즉시 무효화하기 어렵다는 반대급부가 있다 — 그래서 수명이 짧은 액세스 토큰과 재발급용 리프레시 토큰을 나누는 패턴이 표준처럼 쓰인다.

정리하면 **세션은 "서버가 기억"이라 통제가 쉽고 확장이 숙제, 토큰은 "클라이언트가 소지"라 확장이 쉽고 회수가 숙제**다. 어느 쪽이든 HTTP가 무상태라는 사실은 변하지 않고, 기억의 위치만 옮겨 다닌다.

## 쿠키 속성 — 자동 전송의 안전장치

쿠키의 강력함은 "자동으로 붙는다"인데, 사실 이게 그대로 약점이기도 하다. 자동으로 붙기 때문에, 위의 `Set-Cookie`에 달려 있던 속성들이 전부 방어 장치다.

- **HttpOnly**: 자바스크립트(`document.cookie`)로 읽을 수 없게 한다. XSS로 스크립트가 주입돼도 쿠키 탈취는 막는다. 로그인 토큰을 localStorage가 아닌 HttpOnly 쿠키에 두라는 조언의 근거다.
- **Secure**: HTTPS에서만 전송한다. 평문 HTTP로 쿠키가 새는 것을 막는다.
- **SameSite**: 다른 사이트에서 시작된 요청에 쿠키를 붙일지 정한다. 악성 사이트가 사용자의 브라우저를 시켜 "쿠키가 자동으로 붙은 요청"을 우리 서버에 날리는 공격(CSRF)의 방어선이다. 크롬 등 다수 브라우저가 기본값으로 채택한 `Lax`는 대부분의 크로스 사이트 요청에서 쿠키를 제외한다.
- **Max-Age / Expires**: 수명. 지정하지 않으면 브라우저를 닫을 때 사라지는 세션 쿠키가 된다.

개인적으로 이 속성들을 공부하고 나서야, 프로젝트에서 JWT를 직접 구현할 때 왜 굳이 HttpOnly 쿠키에 토큰을 실었는지가 명확해졌다. localStorage는 XSS 한 방에 토큰이 통째로 새지만, HttpOnly 쿠키는 스크립트가 손댈 수 없다(물론 막는 건 탈취까지다 — 주입된 스크립트가 그 브라우저 안에서 인증된 요청을 대신 보내는 것은 별개의 문제다). 대신 자동 전송이라는 성질 때문에 CSRF를 SameSite로 다시 막아야 한다 — 저장 위치의 선택이 곧 방어해야 할 공격의 선택이었다.

---

로그인 유지는 HTTP가 상태를 갖게 된 게 아니라, **무상태 프로토콜 위에서 클라이언트가 증명서를 매번 들고 다니는 관례**다 — 증명서의 실체가 서버 저장소의 열쇠면 세션, 서명된 정보 자체면 토큰이다.

그런데 브라우저가 서버 몰래 알아서 해주는 일이 쿠키 전송 말고도 하나 더 있다. 한 번 받은 파일을 다시 받지 않는 것 — 두 번째 방문이 첫 방문보다 빠른 이유다. → [같은 파일을 두 번 받지 않는 방법](/network/09-http-caching)
