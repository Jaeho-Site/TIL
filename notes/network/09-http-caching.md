# 같은 파일을 두 번 받지 않는 방법

개발자 도구 Network 탭을 열고 사이트를 새로고침하다 보면 상태 코드가 미묘하게 섞여 있는 걸 보게 된다.

```
main.a3f8b2.js     200 (from disk cache)   0ms
logo.png           200 (from memory cache) 0ms
/api/profile       304 Not Modified        48ms
/api/posts         200 OK                  180ms
```

공부하다 여기서 막혔다. `200 (from disk cache)`와 `304 Not Modified`는 **둘 다 "캐시를 썼다"는 뜻 아닌가? 왜 하나는 0ms고 하나는 48ms일까?**

답부터 말하면, 앞의 것은 **서버에 물어보지도 않은 것**이고 뒤의 것은 **"그대로 써도 되나요?" 하고 물어본 뒤 재사용한 것**이다. 캐시에는 이렇게 두 단계가 있고, 이 구분이 HTTP 캐싱의 뼈대다.

## 1단계 — 신선한 동안은 묻지도 않는다

서버는 응답을 줄 때 "이 응답을 얼마나 믿어도 되는지"를 헤더로 알려줄 수 있다.

```
Cache-Control: max-age=3600
```

"앞으로 3600초 동안은 신선(fresh)하다"는 뜻이다. 이 기간 안에 같은 리소스가 필요해지면, 브라우저는 **네트워크에 나가지 않고** 저장해 둔 사본을 그냥 쓴다. 그게 `200 (from disk cache)` — 요청 자체가 발생하지 않았으니 0ms다. [빠르게 보내면 왜 안 되나](/network/03-flow-congestion)에서 본 온갖 노력들이 무색하게, **가장 빠른 요청은 보내지 않는 요청**이다.

## 2단계 — 유통기한이 지나면 "재검증"한다

max-age가 지나 상한(stale) 상태가 되면 캐시를 바로 버릴까? 아니다. 유통기한이 지났다고 내용까지 바뀌었다는 보장은 없으니, 브라우저는 서버에 **조건부 요청**을 보낸다.

서버가 처음 응답할 때 리소스의 지문을 함께 보냈다면 —

```
ETag: "33a64df5"
```

브라우저는 재검증 시 그 지문을 제시한다.

```
GET /api/profile HTTP/1.1
If-None-Match: "33a64df5"
```

서버는 현재 리소스의 지문과 비교해서, 같으면 본문 없이 **`304 Not Modified`**만 돌려준다 — "네가 가진 그대로 써." 왕복 한 번(48ms)은 들었지만 본문 전송은 아꼈다. 다르면 새 본문과 새 ETag를 담은 200을 준다. ETag 대신 수정 시각(`Last-Modified` / `If-Modified-Since`)으로 재검증하는 고전적인 방법도 있는데, 초 단위 정밀도라 지문 비교인 ETag가 더 정확하다.
