# 네트워크는 왜 계층으로 나눴나

네트워크 공부를 시작하면서 스스로에게 던진 첫 질문이 있다. 매일 쓰는 코드 한 줄에서 출발했다.

```javascript
fetch('https://ezilog.dev/api/posts');
```

이 한 줄이 만든 요청이 서버에 도착하려면, **주소가 몇 개 필요할까?**

나는 당연히 하나라고 생각했다. 도메인이 IP 주소로 바뀌고, 그 IP로 찾아가면 끝 아닌가. 그런데 답은 **세 개**다. IP 주소만으로는 요청이 서버 프로세스까지 도착하지 못한다.

## IP 하나로는 왜 부족한가

서버 컴퓨터에 도착했다고 치자. 그 컴퓨터 안에는 웹 서버, 데이터베이스, ssh 데몬까지 여러 프로그램이 동시에 떠 있다. **이 데이터가 어느 프로그램의 것인지** IP 주소는 말해주지 않는다. 그리고 애초에 그 컴퓨터까지 가는 길도 문제다. 내 요청은 서버로 순간이동하는 게 아니라 공유기, 통신사 라우터, 백본망을 거쳐 **한 장비씩 건너뛰며** 이동한다. 각 구간에서는 "다음에 넘겨줄 장비"를 가리킬 주소가 따로 필요하다.

그래서 주소가 세 종류다.

| 계층 | 식별자 | 가리키는 것 |
|---|---|---|
| L4 전송 | 포트 번호 | 호스트 안의 **프로세스** (어떤 프로그램인지) |
| L3 네트워크 | IP 주소 | 네트워크 위의 **호스트** (어떤 컴퓨터인지) |
| L2 데이터 링크 | MAC 주소 | 물리적으로 인접한 **다음 장비** |

택배에 비유하면 IP는 아파트 건물 주소, 포트는 동호수다. 그리고 MAC 주소는 최종 주소가 아니라 "다음 물류 허브"다. 배송 조회를 해보면 택배는 목적지로 직행하지 않고 허브를 여러 번 거치는데, 각 구간의 이동은 "지금 당장 어느 허브로 보낼 것인가"만 알면 된다. 패킷도 똑같다 — IP 헤더의 목적지 주소는 끝까지 유지되지만, MAC 주소는 라우터를 지날 때마다 다음 장비의 것으로 갈아 끼워진다.

주소가 세 종류라는 건, 통신 과정이 **역할이 다른 여러 단계로 나뉘어 있다**는 뜻이다. 이 단계 구분이 바로 계층 모델이다.

## 이론의 OSI 7계층, 실체의 TCP/IP 4계층

책과 문서를 오가며 공부하다 보면 이런 말을 자주 만난다. "OSI 7계층은 이론이고, 실전에서는 TCP/IP 4계층을 봐야 한다."

두 모델의 관계는 **요리 레시피와 실제 요리**에 비유하면 선명해진다. 레시피에는 재료 준비, 손질, 조리, 플레이팅이 체계적으로 나뉘어 있지만, 실제 주방에서는 몇 단계가 동시에 진행되거나 합쳐진다. OSI는 통신이 어떤 기능 단위로 나뉘어야 하는지를 설명하는 레시피(개념 모델)이고, TCP/IP는 실제 인터넷을 움직이는 요리 과정(구현체)이다.

```
OSI 7계층                TCP/IP 4계층
─────────────           ─────────────
7 응용                 ┐
6 표현                 │→ 응용 (HTTP, DNS, TLS ...)
5 세션                 ┘
4 전송                  → 전송 (TCP, UDP)
3 네트워크              → 인터넷 (IP)
2 데이터 링크          ┐
1 물리                 ┘→ 네트워크 액세스 (이더넷, Wi-Fi)
```

OSI의 세션(L5)·표현(L6) 계층이 하는 일 — 세션 관리, 암호화, 데이터 직렬화 — 은 현대 시스템에서 독립 계층으로 존재하지 않고 애플리케이션이나 라이브러리가 직접 처리한다. 그래서 TCP/IP 모델은 셋을 응용 계층 하나로 묶는다.

그럼 왜 굳이 계층을 나눴을까. 한마디로 **관심사의 분리**다. 와이파이를 쓰다가 유선 랜으로 바꿔도 `fetch` 코드는 한 글자도 바뀌지 않는다. 물리적 전송 수단의 변화가 하위 계층 안에서 흡수되고, 상위 계층은 아래가 어떻게 돌아가는지 몰라도 되기 때문이다. 각 계층은 자기 역할만 수행하고 위아래와는 정해진 방식으로만 상호작용한다 — 사실 우리가 컴포넌트를 나누고 인터페이스를 정의하는 이유와 정확히 같다.

## 캡슐화 — 계층을 내려가며 포장이 늘어난다

계층이 "역할 분담표"라면, 실제 데이터가 그 계층들을 통과하는 과정이 **캡슐화**(encapsulation)다. 각 계층은 자기 역할에 필요한 제어 정보 — 위에서 본 식별자들 — 를 데이터 앞에 **헤더**로 덧붙인다. 마트에서 산 물건을 비닐에 담고, 상자에 넣고, 송장을 붙이는 포장 과정과 같다.

계층마다 데이터를 부르는 이름(PDU)도 달라진다.

![캡슐화 과정 — 응용 계층의 스트림이 TCP 헤더를 붙여 세그먼트, IP 헤더를 붙여 패킷, MAC 헤더와 FCS를 붙여 프레임이 되는 과정](/images/network/01-encapsulation.png)

- **스트림(L7)**: 애플리케이션이 만든 순수 데이터. 경계 없는 바이트의 흐름
- **세그먼트(L4)**: 스트림을 전송 가능한 크기로 자르고 TCP 헤더(포트 번호, 순서 번호)를 붙인 것
- **패킷(L3)**: 세그먼트에 IP 헤더(출발지·목적지 IP)를 붙인 것. 라우팅의 기본 단위
- **프레임(L2)**: 패킷에 MAC 헤더를 붙이고, 끝에는 전송 오류 검출용 FCS까지 붙여 밀봉한 것

수신 측은 정확히 역순이다. 프레임에서 MAC 헤더를 벗기고, IP 헤더를 벗기고, TCP 헤더를 확인해 포트 번호에 맞는 프로세스의 소켓으로 데이터를 올려보낸다(역캡슐화). 택배 언박싱이다.

### 어디까지 잘라서 보내나 — MTU와 MSS

"전송 가능한 크기로 자른다"의 기준도 정해져 있다. 이더넷 환경에서 한 번에 실어 보낼 수 있는 최대 크기(**MTU**)는 1500바이트다. 여기서 IP 헤더 20바이트와 TCP 헤더 20바이트를 빼면, 실제 데이터가 실릴 수 있는 최대 크기(**MSS**)는 1460바이트가 된다. 2MB짜리 이미지를 요청하면 TCP가 이걸 1460바이트 단위로 약 1,400개로 토막 내서 보낸다는 뜻이다.

## 그런데 이 포장은 누가 하나?

`fetch`를 호출한 브라우저가 직접 TCP 헤더를 만들까? 아니다. 찾아보니 여기에도 계층이 있었다. 브라우저 같은 애플리케이션은 유저 모드에서 돌고, TCP/IP 스택은 운영체제 **커널** 안에 구현되어 있다. 애플리케이션은 커널이 열어준 **소켓**이라는 통로에 데이터를 밀어 넣을 뿐이고, 자르고 헤더를 붙이는 포장 작업은 전부 커널이 한다. 소켓은 운영체제 입장에서 일종의 특별한 파일이라, 개발자는 파일을 읽고 쓰듯 네트워크를 다룬다 — 그리고 각 소켓 연결은 출발지·목적지 IP와 포트, 프로토콜의 조합(5-tuple)으로 식별된다.

개인적으로 이 구조를 알고 나서야 "프론트엔드 개발자가 TCP를 몰라도 코드는 돌아가는" 이유가 납득됐다. 소켓이 하위 계층의 복잡성을 완전히 숨겨주기 때문이다. 다만 숨겨져 있다는 것과 없다는 것은 다르다 — 요청이 느릴 때, 연결이 끊길 때, 문제는 그 숨겨진 계층에서 일어난다.

이 계층 구분은 디버깅에서 그대로 무기가 된다. 페이지가 안 뜰 때 "DNS가 안 풀리나(응용) → 연결 자체가 안 되나(전송) → 서버가 죽었나" 순으로 계층을 따라 내려가며 원인을 좁힐 수 있다. 개발자 도구 Network 탭의 Timing이 요청 하나를 DNS Lookup, Initial connection, TTFB로 쪼개 보여주는 것도 이 계층을 따라 내려가는 순서와 겹친다.

---

계층 모델은 통신이라는 거대한 문제를 역할별로 쪼갠 관심사의 분리이고, 캡슐화는 각 계층이 자기 몫의 주소를 헤더로 덧붙이는 과정이다.
