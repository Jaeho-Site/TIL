# URL을 입력하면 무슨 일이 일어나나

주소창에 `https://ezilog.dev`를 치고 엔터를 누른다. 화면에 페이지가 뜨기까지 — 그 사이에 무슨 일이 일어날까.

사실 이 질문은 이 카테고리를 시작한 이유였다. 처음엔 "서버에 요청이 가고 응답이 온다" 한 문장이 답의 전부였는데, 열다섯 편을 지나온 지금은 그 한 문장 안에 접혀 있던 단계들이 전부 보인다. 새로운 개념 없이, 이번엔 순서대로 꿰기만 해보자.

![URL 입력부터 화면까지의 전체 여정 지도 — DNS 조회, TCP 핸드셰이크, TLS 핸드셰이크, HTTP 요청과 응답을 거쳐 렌더링으로 이어지는 흐름](/images/network/16-url-journey.png)

## 0. 사실, 출발하기 전에 — 캐시 판정

여정을 시작하기 전에 브라우저가 가장 먼저 하는 일이 있다. [캐시 판정](/network/09-http-caching)이다. 이 URL의 **신선한 사본**이 캐시에 있다면 아래의 모든 단계 — DNS도, 연결도, 요청도 — 가 통째로 생략된다. 가장 빠른 요청은 보내지 않는 요청이니까. 사본이 없거나 상했을 때만 진짜 여정이 시작된다.

## 1. 이름을 주소로 — DNS

캐시로 끝나지 않았다면, 브라우저가 먼저 할 일은 `ezilog.dev`라는 이름을 IP 주소로 바꾸는 것이다. [브라우저 캐시 → 운영체제 캐시 → 리졸버](/network/12-dns) 순으로 가까운 기억부터 뒤지고, 다 비었으면 리졸버가 루트 → TLD → 권한 네임서버로 이어지는 분산 탐색을 대신 해준다. 이 답이 나와야 다음 모든 단계가 시작된다 — DNS가 파이프라인의 입구인 이유다.

## 2. 연결 — TCP 3-way 핸드셰이크

IP를 알았으니 그 호스트의 443 포트로 연결을 수립한다. [SYN, SYN+ACK, ACK 세 번의 인사](/network/02-tcp-handshake)로 양쪽이 순서 번호를 합의하고 연결 상태를 기억한다. 이제 [계층 모델](/network/01-layered-model)에서 본 것처럼, 내 데이터는 세그먼트→패킷→프레임으로 겹겹이 포장되어 라우터들을 건너뛸 준비가 됐다.

## 3. 암호화 합의 — TLS 핸드셰이크

`https`이므로 대화 전에 [TLS 핸드셰이크](/network/10-https-tls)가 이어진다. ClientHello에 Key Share를 실어 보내고, 서버의 인증서를 신뢰 사슬을 따라 Root CA까지 검증하고, 세션키를 합의한다 — TLS 1.3이면 이 전부가 1왕복이다. 이 시점까지 실제 HTTP는 한 글자도 오가지 않았는데 왕복이 벌써 몇 번 쌓였다. [HTTP/3가 TCP와 TLS의 왕복을 QUIC 하나로 합친 것](/network/07-http-evolution)이 바로 이 누적 때문이었다.

## 4. 드디어 대화 — HTTP 요청과 응답

이제 암호화된 연결 위로 [HTTP 요청 메시지](/network/05-http-message)가 나간다. `GET /`으로 시작하는 요청 — 어떤 버전의 HTTP로 말할지는 방금 TLS 핸드셰이크에서 이미 합의됐다(ALPN 확장). Host를 비롯한 헤더들과 [저장돼 있던 쿠키](/network/08-cookie-session)가 자동으로 실린다 — 로그인돼 있다면 서버가 나를 알아보는 근거다. 서버는 [상태 코드](/network/06-method-status)로 결과를 요약한 응답을 돌려준다. 200이면 본문에 HTML이 담겨 있다.

0단계에서 상한 사본을 쥐고 온 경우라면 이 요청은 [조건부 요청](/network/09-http-caching)이 된다 — 내용이 그대로면 304로 본문 전송을 아낀다.

## 5. HTML이 부르는 후속 요청들

받은 HTML을 파싱하다 보면 CSS, 자바스크립트, 이미지, 폰트가 줄줄이 필요해진다. [HTTP/2 멀티플렉싱](/network/07-http-evolution) 덕에 이 수십 개의 요청은 한 연결 위에서 줄 서기 없이 뒤섞여 흐른다. 다른 도메인의 리소스라면 DNS부터 다시 시작인데, [미리 걸어둔 dns-prefetch·preconnect](/network/12-dns)가 그 입구 비용을 지워준다. API 호출이 있다면 [fetch가](/network/13-ajax-fetch) [CORS의 허가 절차](/network/11-sop-cors)를 통과해 데이터를 받아온다.

## 6. 그리고 화면으로

여기서부터는 네트워크의 영역이 아니다. 받은 HTML과 CSS로 DOM과 CSSOM을 만들고 렌더 트리를 그리는 이야기 — 그건 [Browser 카테고리의 렌더링 파이프라인](/browser/01-rendering-pipeline)이 이어받는다. 네트워크 노트의 바톤은 여기까지다.

## 전체를 한 번에

```
주소창 엔터
 → 캐시 판정 (신선한 사본이 있으면 전부 생략)  [09]
 → DNS 조회 (캐시 3단 → 분산 탐색)           [12]
 → TCP 3-way 핸드셰이크                       [01·02]
 → TLS 핸드셰이크 (인증서 검증, 세션키 합의)   [10]
 → HTTP 요청 (쿠키 자동 첨부, 상했으면 조건부) [05·08]
 → 서버 응답 (상태 코드 + HTML, 또는 304)      [06·09]
 → 후속 리소스 병렬 수신 (멀티플렉싱, CORS)    [07·11·13]
 → 렌더링 시작                                [→ Browser]
```

정리하면서 새삼 느낀 건, 이 여정의 절반이 **대화가 아니라 대화의 준비**라는 점이다. 이름을 찾고, 연결을 맺고, 암호를 합의하는 왕복들 — 그리고 이 카테고리에서 본 진화의 대부분(keep-alive, 멀티플렉싱, QUIC, 0-RTT, 캐싱, preconnect)은 결국 그 준비 왕복을 줄이거나 없애려는 노력이었다. 네트워크 최적화라는 말이 거창해 보였는데, 본질은 하나였다. **기다림을 만드는 왕복을 세고, 하나씩 지우는 것.**

---

URL 입력 뒤에 일어나는 일은 마법이 아니라, 이름 해석(DNS) → 연결(TCP) → 신뢰(TLS) → 대화(HTTP)라는 합의의 사슬이다. 그리고 각 고리는 저마다의 이유로 지금의 모습이 됐다 — 그 이유들을 따라온 것이 이 열여섯 편이었다.
