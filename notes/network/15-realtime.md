# 서버가 먼저 말을 걸 수 있나

채팅이나 알림 기능을 처음 구상해보면 바로 벽에 부딪힌다. 지금까지 본 HTTP 통신은 전부 **클라이언트가 묻고 서버가 답하는** 구조였다. 그런데 "새 메시지 도착"이라는 사건은 서버 쪽에서 생긴다. 서버는 브라우저에게 먼저 연락할 방법이 없는데, 이 소식을 어떻게 전할까?

> HTTP의 요청-응답 모델만 가지고 실시간 알림을 흉내 낸다면, 어떻게 해야 할까?

내가 처음 떠올린 답은 하나뿐이었다 — "계속 물어보면 되지 않나?" 사실 그게 정답의 첫 번째 형태다.

## 폴링 — 계속 물어보기

**폴링**(polling)은 클라이언트가 주기적으로 "새 소식 있어?"를 반복하는 방식이다.

```javascript
setInterval(async () => {
  const res = await fetch('/api/notifications');
  // 대부분의 응답: "없음"
}, 3000);
```

단순하고 어디서나 동작한다. 대신 두 가지를 포기한다. **실시간성** — 3초 주기면 최악의 경우 3초 늦는다. 그리고 **효율** — 소식이 없어도 요청은 계속 나가고, [매 요청에는 헤더와 쿠키가 통째로 실린다](/network/08-cookie-session). 응답의 대부분이 "없음"인 통신에 이 비용은 아깝다.

개선형이 **롱 폴링**(long polling)이다. 서버가 "없음"을 즉시 답하지 않고, **새 소식이 생길 때까지 응답을 붙들고 있다가** 소식이 생기면 그때 응답한다. 클라이언트는 응답을 받자마자 다시 요청을 걸어둔다. 실시간성은 좋아지지만, 여전히 소식 하나마다 요청-응답 한 사이클을 새로 돈다.

## SSE — 응답을 끝내지 않는다는 발상

**SSE**(Server-Sent Events)는 더 우아한 절충이다. 클라이언트가 한 번 요청하면, 서버는 응답을 **영원히 끝내지 않고** 그 스트림에 이벤트가 생길 때마다 텍스트 조각을 흘려보낸다. HTTP 응답이 곧 열린 파이프가 되는 것이다.

```javascript
const es = new EventSource('/api/notifications/stream');
es.onmessage = (e) => console.log(JSON.parse(e.data));
```

브라우저 내장 `EventSource`가 연결이 끊기면 **자동으로 재연결**까지 해준다. 방향이 서버→클라이언트 단방향이라는 게 제약이자 특징이다 — 클라이언트가 보낼 말은 평범한 fetch로 따로 보내면 된다. 알림, 주가·모니터링 대시보드, 그리고 요즘 흔히 보는 AI 챗봇의 글자 단위 스트리밍 응답까지, "서버가 일방적으로 흘려보내는" 시나리오에 정확히 맞는 도구다. 평범한 HTTP 위에서 동작하므로 인프라도 그대로 쓴다. 한 가지 캐비앳이라면, HTTP/1.1 환경에서는 이 열린 연결이 도메인당 동시 연결 6개 중 하나를 상시 점유한다는 것 — HTTP/2 멀티플렉싱 위에서는 사라지는 걱정이다.
