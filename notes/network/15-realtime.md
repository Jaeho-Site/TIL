# 서버가 먼저 말을 걸 수 있나

채팅이나 알림 기능을 처음 구상해보면 바로 벽에 부딪힌다. 지금까지 본 HTTP 통신은 전부 **클라이언트가 묻고 서버가 답하는** 구조였다. 그런데 "새 메시지 도착"이라는 사건은 서버 쪽에서 생긴다. 서버는 브라우저에게 먼저 연락할 방법이 없는데, 이 소식을 어떻게 전할까?

> HTTP의 요청-응답 모델만 가지고 실시간 알림을 흉내 낸다면, 어떻게 해야 할까?

내가 처음 떠올린 답은 하나뿐이었다 — "계속 물어보면 되지 않나?" 사실 그게 정답의 첫 번째 형태다.

## 폴링 — 계속 물어보기

**폴링**(polling)은 클라이언트가 주기적으로 "새 소식 있어?"를 반복하는 방식이다.

```javascript
setInterval(async () => {
  const res = await fetch('/api/notifications');
  // 대부분의 응답: "없음"
}, 3000);
```

단순하고 어디서나 동작한다. 대신 두 가지를 포기한다. **실시간성** — 3초 주기면 최악의 경우 3초 늦는다. 그리고 **효율** — 소식이 없어도 요청은 계속 나가고, [매 요청에는 헤더와 쿠키가 통째로 실린다](/network/08-cookie-session). 응답의 대부분이 "없음"인 통신에 이 비용은 아깝다.

개선형이 **롱 폴링**(long polling)이다. 서버가 "없음"을 즉시 답하지 않고, **새 소식이 생길 때까지 응답을 붙들고 있다가** 소식이 생기면 그때 응답한다. 클라이언트는 응답을 받자마자 다시 요청을 걸어둔다. 실시간성은 좋아지지만, 여전히 소식 하나마다 요청-응답 한 사이클을 새로 돈다.

## SSE — 응답을 끝내지 않는다는 발상

**SSE**(Server-Sent Events)는 더 우아한 절충이다. 클라이언트가 한 번 요청하면, 서버는 응답을 **영원히 끝내지 않고** 그 스트림에 이벤트가 생길 때마다 텍스트 조각을 흘려보낸다. HTTP 응답이 곧 열린 파이프가 되는 것이다.

```javascript
const es = new EventSource('/api/notifications/stream');
es.onmessage = (e) => console.log(JSON.parse(e.data));
```

브라우저 내장 `EventSource`가 연결이 끊기면 **자동으로 재연결**까지 해준다. 방향이 서버→클라이언트 단방향이라는 게 제약이자 특징이다 — 클라이언트가 보낼 말은 평범한 fetch로 따로 보내면 된다. 알림, 주가·모니터링 대시보드, 그리고 요즘 흔히 보는 AI 챗봇의 글자 단위 스트리밍 응답까지, "서버가 일방적으로 흘려보내는" 시나리오에 정확히 맞는 도구다. 평범한 HTTP 위에서 동작하므로 인프라도 그대로 쓴다. 한 가지 캐비앳이라면, HTTP/1.1 환경에서는 이 열린 연결이 도메인당 동시 연결 6개 중 하나를 상시 점유한다는 것 — HTTP/2 멀티플렉싱 위에서는 사라지는 걱정이다.

## 웹소켓 — 아예 다른 대화 규칙으로 갈아탄다

채팅처럼 **양방향**이 잦고 지연에 민감한 통신이라면, HTTP의 문법 자체를 벗어나는 선택지가 있다. **웹소켓**(WebSocket)이다.

재미있는 건 시작 방식이다. 웹소켓 연결은 HTTP 요청으로 시작한다.

```
GET /chat HTTP/1.1
Upgrade: websocket
Connection: Upgrade
(일부 헤더 생략)

HTTP/1.1 101 Switching Protocols
```

"이 연결, HTTP 말고 웹소켓 규칙으로 바꿔 쓰자"는 **프로토콜 전환 요청**이고, 서버가 101로 수락하면 그 순간부터 [같은 TCP 연결](/network/02-tcp-handshake) 위에서 HTTP가 아닌 웹소켓 프레임이 오간다. 이후로는 요청-응답 짝도, 매번 붙는 헤더도 없다 — **양쪽 모두 아무 때나** 작은 프레임으로 메시지를 보낸다. 80·443 포트와 HTTP 핸드셰이크를 빌려 시작하는 덕분에 기존 웹 인프라(방화벽)를 그대로 통과한다는 것도 설계 포인트다 — [QUIC이 UDP를 빌려 탄 것](/network/04-tcp-vs-udp)과 같은 종류의 실용주의다.

대가는 운영 복잡도다. "항상 열려 있는 연결"은 [무상태 HTTP](/network/05-http-message)와 달리 서버가 연결마다 상태를 유지해야 한다는 뜻이고, 서버를 여러 대로 늘릴 때 연결들을 어떻게 나누고 서로의 메시지를 어떻게 전파할지가 새 숙제가 된다.

## 어느 것을 쓰나

| | 폴링 | SSE | 웹소켓 |
|---|---|---|---|
| 방향 | 클라이언트 주도 | 서버 → 클라이언트 | 양방향 |
| 실시간성 | 주기만큼 지연 | 즉시 | 즉시 |
| 프로토콜 | HTTP 그대로 | HTTP 그대로 | 전환(101) 후 자체 규칙 |
| 재연결 | 해당 없음 | 브라우저가 자동 | 직접 구현 |
| 어울리는 곳 | 갱신이 느긋한 데이터 | 알림, 피드, AI 스트리밍 | 채팅, 게임, 협업 편집 |

개인적으로 이 셋을 공부하고 얻은 기준은 "**화려한 쪽이 아니라 덜 과한 쪽을 고른다**"였다. 양방향이 정말 필요한 게 아니라면 웹소켓의 운영 비용을 질 이유가 없고, 몇 초 늦어도 되는 데이터라면 폴링으로 충분하다 — 사실 폴링은 TanStack Query의 `refetchInterval` 한 줄이면 끝이라, 단순함의 가치가 생각보다 크다.

세 방식은 전부 "서버는 먼저 말을 걸 수 없다"는 HTTP의 전제를 각자의 방식으로 우회한 것이다 — 폴링은 자주 물어서, SSE는 응답을 끝내지 않아서, 웹소켓은 대화 규칙 자체를 바꿔서.
