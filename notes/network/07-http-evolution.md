# HTTP는 왜 세 번 다시 태어났나

개발자 도구 Protocol 열을 켜보면 같은 페이지 안에서도 `http/1.1`, `h2`, `h3`가 섞여 있다. 공부하다 이 지점에서 막혔던 질문이 있다.

> HTTP/2가 요청을 "동시에" 처리한다는데, HTTP/1.1의 keep-alive도 연결을 재사용하지 않나. 뭐가 다른 거지?

나는 한동안 "재사용"과 "동시"를 같은 말로 이해하고 있었다. 그런데 이 둘은 전혀 다른 층위의 이야기다. 연결을 **재사용**해도 그 위의 대화는 여전히 **한 번에 하나씩**일 수 있기 때문이다. HTTP의 세 번의 개정은 전부 이 "한 번에 하나씩"이라는 병목 — 정확히는 **줄 서기(Head-of-Line Blocking)** — 와 싸워온 역사다.

## HTTP/1.1 — 연결은 재사용하지만, 줄은 그대로다

[HTTP 메시지 편](/network/05-http-message)에서 봤듯 HTTP/1.0은 요청 하나마다 연결을 새로 맺고 끊었다. 페이지 하나에 리소스가 수십 개인 시대가 되자 [핸드셰이크 비용](/network/02-tcp-handshake)이 치명적이었고, HTTP/1.1은 지속 연결(keep-alive)을 기본값으로 만들었다.

하지만 연결을 재사용해도 규칙이 하나 남아 있었다. **응답은 요청 순서대로 와야 한다.** 요청을 미리 여러 개 보내는 파이프라이닝이라는 기술도 고안됐지만, 첫 번째 응답이 무거운 API라면 뒤에 줄 선 가벼운 CSS·JS는 앞 응답이 끝날 때까지 서버에서 대기해야 한다. 이게 **HTTP 수준의 HOLB**다. 결국 파이프라이닝은 현대 브라우저에서 사실상 비활성화됐고, 브라우저들은 도메인당 최대 6개의 연결을 열어 병렬을 물리적으로 흉내 내는 우회로에 의존했다.

정적 리소스를 `img1.cdn.com`, `img2.cdn.com`처럼 여러 도메인에 쪼개 두던 도메인 샤딩이라는 기법이 있었다는 것도 이 맥락에서 이해된다 — 연결 6개 제한을 도메인 수로 뚫으려던 시대의 유산이다.

## HTTP/2 — 메시지를 쪼개서 줄 자체를 없애다

2015년의 HTTP/2는 성능 개선판이 아니라 **메시지를 나르는 방식의 재설계**다. 핵심은 텍스트 대신 바이너리 프레이밍을 도입한 것이다. 모든 HTTP 메시지는 프레임이라는 작은 단위로 쪼개지고, 각 프레임에는 자신이 속한 대화를 표시하는 **스트림 ID**가 붙는다.

이게 만들어낸 변화가 **멀티플렉싱**(multiplexing)이다. 하나의 TCP 연결 위에서 여러 요청·응답의 프레임들이 뒤섞여 흐르고, 수신 측이 스트림 ID로 다시 조립한다. 무거운 응답이 진행 중이어도 다른 응답의 프레임이 그 사이사이에 끼어 전송되므로, 요청들이 줄을 설 필요가 없다. HTTP 수준의 HOLB가 여기서 풀렸다. 덤으로 매 요청마다 반복되는 Cookie·User-Agent 같은 헤더를 HPACK으로 압축해 오버헤드도 줄였다.

![HTTP/1.1의 순차 응답 대기와 HTTP/2 멀티플렉싱의 비교 — 1.1은 무거운 첫 응답이 끝나야 다음이 시작되지만, 2는 여러 스트림의 프레임이 뒤섞여 동시에 흐른다](/images/network/07-multiplexing.png)

그런데 HTTP/2를 실전에 투입하고 보니, 없앤 줄이 **한 층 아래에서 다시 나타났다.**

## 남은 병목 — 이번엔 TCP가 줄을 세운다

[TCP의 순서 보장](/network/04-tcp-vs-udp)을 떠올려 보자. TCP는 패킷 하나가 유실되면 그것이 재전송되어 도착할 때까지, 뒤에 멀쩡히 도착한 데이터를 애플리케이션에 올려주지 않는다. TCP 입장에서는 스트림이고 뭐고 없다 — 그저 하나의 바이트 흐름이고, 순서가 맞을 때까지 전부 대기다.

HTTP/2가 수백 개의 스트림을 하나의 TCP 연결에 몰아넣자 이 특성이 정면으로 부딪혔다. 이미지 스트림의 패킷 하나가 유실됐을 뿐인데, 그 뒤에 도착한 자바스크립트 스트림의 프레임까지 전부 커널 버퍼에 묶인다. **논리적으로는 병렬인데, 물리적으로는 여전히 한 줄이다.** 이게 TCP 수준의 HOLB이고, 패킷 유실이 잦은 모바일 환경에서 특히 아프게 체감됐다.

## HTTP/3 — 전송 계층을 갈아 끼우다

애플리케이션 계층에서 할 수 있는 건 다 했다. 남은 원인은 TCP 자체인데, 앞서 봤듯 TCP는 커널에 있어 고칠 수 없고, 새 전송 프로토콜은 미들박스들이 통과시켜 주지 않는다. 그래서 HTTP/3는 UDP 위에 유저 영역으로 전송 계층을 새로 지은 QUIC 위에서 돈다.

QUIC이 TCP HOLB를 끊어낸 방법은 명쾌하다. **순서 보장과 전달 대기의 범위를 연결 전체가 아니라 스트림 단위로 좁혔다.** 이미지 스트림에서 패킷이 유실되면 그 스트림만 잠시 멈추고, CSS·JS 스트림은 아무 일 없이 계속 흐른다. 유실의 영향 범위가 드디어 유실된 대화 하나로 좁혀진 것이다.

지연 시간에서도 이득이 있다. QUIC은 TLS 1.3을 프로토콜 안에 통합해 전송 연결 수립과 암호화 협상을 한 번에 처리한다 — 최초 연결도 1-RTT, 한 번 접속했던 서버라면 0-RTT로 첫 요청을 바로 실어 보낼 수 있다. 다만 0-RTT는 같은 요청이 재전송되는 리플레이 공격에 취약해서, [멱등성이 보장되는](/network/06-method-status) 안전한 요청에만 제한적으로 쓰인다 — 멱등성 개념이 전송 계층 설계에까지 등장하는 장면이다.

모바일에서의 변화도 크다. TCP 연결은 IP·포트 조합으로 식별되므로 와이파이에서 LTE로 바뀌는 순간 끊긴다. QUIC은 별도의 Connection ID로 연결을 식별해서, IP가 바뀌어도 같은 연결이 이어진다. 이동 중에 스트리밍이 안 끊기는 이유다.

## 세 번의 개정을 한 줄씩으로 줄이면

- **1.1**: 연결을 재사용하자 (그러나 응답은 한 줄로 — HTTP HOLB)
- **2**: 메시지를 프레임으로 쪼개 한 연결에 섞어 보내자 (그러나 TCP가 한 줄로 — TCP HOLB)
- **3**: 그럼 전송 계층을 스트림 단위로 다시 만들자 (QUIC)

개인적으로 이 흐름에서 인상 깊었던 건, 각 버전이 이전 버전의 해결책 **때문에** 드러난 문제를 푼다는 점이다. 멀티플렉싱은 1.1의 줄 서기를 없앴지만, 스트림을 한 연결에 몰아넣었기에 TCP의 줄 서기를 드러냈다. 해결이 다음 문제의 원인이 되는 진화였다.

HTTP의 세 번의 개정은 기능 추가가 아니라 "**줄 서기를 어느 층에서 없앨 것인가**"라는 하나의 문제를 계층을 내려가며 푼 과정이다 — 1.1은 연결 재사용으로, 2는 애플리케이션 계층의 멀티플렉싱으로, 3는 전송 계층 교체로.
