# HTTP는 왜 세 번 다시 태어났나

개발자 도구 Protocol 열을 켜보면 같은 페이지 안에서도 `http/1.1`, `h2`, `h3`가 섞여 있다. 공부하다 이 지점에서 막혔던 질문이 있다.

> HTTP/2가 요청을 "동시에" 처리한다는데, HTTP/1.1의 keep-alive도 연결을 재사용하지 않나. 뭐가 다른 거지?

나는 한동안 "재사용"과 "동시"를 같은 말로 이해하고 있었다. 그런데 이 둘은 전혀 다른 층위의 이야기다. 연결을 **재사용**해도 그 위의 대화는 여전히 **한 번에 하나씩**일 수 있기 때문이다. HTTP의 세 번의 개정은 전부 이 "한 번에 하나씩"이라는 병목 — 정확히는 **줄 서기(Head-of-Line Blocking)** — 와 싸워온 역사다.

## HTTP/1.1 — 연결은 재사용하지만, 줄은 그대로다

[HTTP 메시지 편](/network/05-http-message)에서 봤듯 HTTP/1.0은 요청 하나마다 연결을 새로 맺고 끊었다. 페이지 하나에 리소스가 수십 개인 시대가 되자 [핸드셰이크 비용](/network/02-tcp-handshake)이 치명적이었고, HTTP/1.1은 지속 연결(keep-alive)을 기본값으로 만들었다.

하지만 연결을 재사용해도 규칙이 하나 남아 있었다. **응답은 요청 순서대로 와야 한다.** 요청을 미리 여러 개 보내는 파이프라이닝이라는 기술도 고안됐지만, 첫 번째 응답이 무거운 API라면 뒤에 줄 선 가벼운 CSS·JS는 앞 응답이 끝날 때까지 서버에서 대기해야 한다. 이게 **HTTP 수준의 HOLB**다. 결국 파이프라이닝은 현대 브라우저에서 사실상 비활성화됐고, 브라우저들은 도메인당 최대 6개의 연결을 열어 병렬을 물리적으로 흉내 내는 우회로에 의존했다.

정적 리소스를 `img1.cdn.com`, `img2.cdn.com`처럼 여러 도메인에 쪼개 두던 도메인 샤딩이라는 기법이 있었다는 것도 이 맥락에서 이해된다 — 연결 6개 제한을 도메인 수로 뚫으려던 시대의 유산이다.

## HTTP/2 — 메시지를 쪼개서 줄 자체를 없애다

2015년의 HTTP/2는 성능 개선판이 아니라 **메시지를 나르는 방식의 재설계**다. 핵심은 텍스트 대신 바이너리 프레이밍을 도입한 것이다. 모든 HTTP 메시지는 프레임이라는 작은 단위로 쪼개지고, 각 프레임에는 자신이 속한 대화를 표시하는 **스트림 ID**가 붙는다.

이게 만들어낸 변화가 **멀티플렉싱**(multiplexing)이다. 하나의 TCP 연결 위에서 여러 요청·응답의 프레임들이 뒤섞여 흐르고, 수신 측이 스트림 ID로 다시 조립한다. 무거운 응답이 진행 중이어도 다른 응답의 프레임이 그 사이사이에 끼어 전송되므로, 요청들이 줄을 설 필요가 없다. HTTP 수준의 HOLB가 여기서 풀렸다. 덤으로 매 요청마다 반복되는 Cookie·User-Agent 같은 헤더를 HPACK으로 압축해 오버헤드도 줄였다.


그런데 HTTP/2를 실전에 투입하고 보니, 없앤 줄이 **한 층 아래에서 다시 나타났다.**
