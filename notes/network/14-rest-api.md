# REST API는 무엇을 약속하나

API 설계를 처음 해보면 반드시 부딪히는 고민이 있다. 할 일 삭제 API의 주소를 뭐라고 지을까?

```
1. GET  /deleteTodo?id=1
2. POST /todos/delete/1
3. DELETE /todos/1
```

셋 다 "동작하게" 만들 수는 있다. 하지만 1번은 [GET으로 삭제하면 왜 안 되는지](/network/06-method-status)에서 본 크롤러 사고의 재현이고, 2번은 행위를 메서드가 아니라 URI에 실었다. 답은 3번인데 — 왜 3번이 "맞다"고 느껴지는 걸까. 그 감각의 정체가 REST다.

## REST — 역할을 나눠 싣는 설계

REST는 특정 기술이 아니라 **HTTP를 설계된 의도대로 쓰기 위한 아키텍처 스타일**이다(HTTP 명세 작업에 참여한 로이 필딩의 논문에서 나왔다). 핵심은 API의 구성 요소를 세 자리에 나눠 싣는 것이다.

| 구성 요소 | 실리는 곳 | 예 |
|---|---|---|
| **자원(Resource)** | URI | `/todos/1` — 1번 할 일 |
| **행위(Verb)** | HTTP 메서드 | `GET` `POST` `PUT` `PATCH` `DELETE` |
| **표현(Representation)** | 본문(페이로드) | `{ "content": "HTTP 공부", "completed": true }` |

이 분담이 지켜지면 URI에는 **명사**만 남는다. `/deleteTodo`처럼 URI에 동사가 들어가는 순간 행위가 두 곳에 실리는 것이고, 그게 1·2번 설계가 어긋나 보이는 이유다.

```
GET    /todos      → 목록 조회
GET    /todos/1    → 1번 조회
POST   /todos      → 생성 (서버가 id를 정한다)
PUT    /todos/1    → 1번 전체 교체
PATCH  /todos/1    → 1번 부분 수정
DELETE /todos/1    → 1번 삭제
```

같은 URI(`/todos/1`)가 메서드에 따라 다른 일을 한다 — 자원은 하나고, 행위만 다르기 때문이다.

## 왜 이 약속이 힘이 있나

처음엔 이게 "깔끔한 네이밍 컨벤션" 정도라고 생각했다. 그런데 [메서드의 안전성·멱등성](/network/06-method-status)과 연결하면 이야기가 달라진다. **메서드에 행위를 실었다는 건, 그 메서드에 딸린 약속들을 전부 상속받는다는 뜻이다.**

`DELETE /todos/1`이라고 선언하는 순간, 클라이언트도 중간의 인프라도 이 요청이 멱등하다는 걸 안다 — 타임아웃이 나면 재시도해도 된다. `GET /todos`는 안전하니 캐시가 응답을 저장해도 된다. 반면 모든 걸 `POST /api`로 보내고 본문 안에 `{"action": "delete"}`를 넣는 설계라면? 기계 입장에선 전부 "멱등하지 않은 불투명한 요청"이라 캐싱도 재시도도 불가능해진다. [상태 코드 편](/network/06-method-status)의 "200에 error: true" 안티 패턴과 정확히 같은 구도다 — **공용어를 버리면 공용어를 알아듣는 인프라의 도움도 버리는 것이다.**

표현(representation)이라는 단어에도 뜻이 있다. 클라이언트가 받는 JSON은 자원 그 자체가 아니라 자원의 한 표현이다. 서버 DB에 어떤 형태로 저장돼 있든, 클라이언트와는 합의된 표현으로만 대화한다 — 내부 구현과 인터페이스의 분리가 여기에도 있다.

## "RESTful하다"의 현실적인 선

그럼 어디까지 지켜야 RESTful일까. 필딩의 논문 기준을 엄격히 적용하면 응답에 다음 행동의 링크까지 담아야 하지만(HATEOAS), 현실의 API 대부분은 거기까지 가지 않는다. 실무에서 통용되는 선은 대체로 이 정도다.

- URI는 명사, 행위는 메서드에
- 계층 관계는 경로로: `/users/42/posts` — 42번 사용자의 글들
- 결과는 [상태 코드](/network/06-method-status)로: 생성이면 201, 없으면 404, 충돌이면 409
- 필터·정렬 같은 부가 조건은 쿼리로: `/todos?completed=true&sort=id`

개인적으로 REST를 공부하고 얻은 가장 큰 실익은 설계보다 **협업 쪽**이었다. 프론트엔드와 백엔드가 API 명세를 논의할 때, REST라는 공통 문법이 있으면 "삭제는 DELETE /todos/:id겠네"가 말 없이도 합의된다. 논쟁이 필요한 건 정말 애매한 지점 — "로그인은 자원이 아닌데 어디에 두지?"(`POST /auth/login` 같은 실용적 타협) — 뿐이다. 약속의 가치는 약속하지 않아도 되는 것들이 늘어나는 데 있다.

---

REST는 자원을 URI에, 행위를 메서드에, 내용을 표현에 나눠 싣는 약속이고, 그 대가로 HTTP 메서드와 상태 코드에 쌓인 모든 합의 — 멱등성, 캐싱, 에러 의미론 — 를 공짜로 물려받는다.

여기까지의 통신은 전부 클라이언트가 먼저 묻고 서버가 답하는 구조였다. 그런데 채팅 알림처럼 **서버 쪽에서 먼저 생기는 사건**은 어떻게 브라우저까지 올까. → [서버가 먼저 말을 걸 수 있나](/network/15-realtime)
