# 페이지를 안 바꾸고 데이터만 받으려면

책을 읽다가 이런 코드를 만났다. 처음 보는 사람에게는 꽤 낯선 모양새다.

```javascript
const xhr = new XMLHttpRequest();
xhr.open('GET', '/todos');
xhr.send();

xhr.onload = () => {
  if (xhr.status === 200) {
    console.log(JSON.parse(xhr.response));
  }
};
```

`fetch` 한 줄이면 될 일을 왜 이렇게 쓰나 싶었는데, 사실 순서가 반대였다. **이 낯선 객체가 없었다면 fetch도, SPA도, 지금의 웹 자체가 없었다.** 이름의 XML부터 이벤트 기반 문법까지, 이 코드에는 웹이 문서에서 애플리케이션으로 넘어온 역사가 눌러 담겨 있다.

## 전통 방식 — 모든 클릭은 페이지 전체를 다시 받는 일이었다

초기 웹에서 서버와의 상호작용은 단 한 가지였다. 링크를 클릭하거나 폼을 제출하면, 브라우저는 **완전한 HTML 문서를 새로 받아 화면 전체를 처음부터 다시 렌더링**했다. 장바구니에 물건 하나를 담아도 페이지 전체가 깜빡이며 다시 그려진다. 바뀐 건 화면 구석의 숫자 하나인데, 변경이 필요 없는 나머지 전부까지 다시 받아오는 것이다 — 전송량도 낭비고, 렌더링을 다시 하는 동안 화면이 순간적으로 끊기는 경험도 피할 수 없었다.

이 구조를 깬 것이 **Ajax**(Asynchronous JavaScript and XML)다. 브라우저가 제공하는 `XMLHttpRequest` 객체로 **자바스크립트가 직접, 비동기로** 서버와 통신하는 방식이다. 페이지 전환 없이 필요한 데이터만 받아서, 바뀌어야 할 부분의 DOM만 갈아 끼운다. 2005년 구글 맵스가 이 방식으로 "드래그하면 지도가 끊김 없이 이어지는" 경험을 보여주면서 웹 전체의 방향이 바뀌었다.

![전통 내비게이션과 Ajax 방식의 비교 — 전통 방식은 클릭마다 HTML 전체를 다시 받아 전체를 다시 그리고, Ajax는 필요한 데이터만 받아 일부 DOM만 갱신한다](/images/network/13-ajax-timeline.png)

이름에 XML이 박혀 있는 건 그 시절의 데이터 교환 형식이 XML이었기 때문이다. 지금은 더 가볍고 자바스크립트 객체와 문법이 거의 같은 **JSON**이 표준이 됐다. 언어 독립적인 텍스트 포맷이라 어떤 서버와도 통하고, `JSON.stringify`(객체→문자열, 직렬화)와 `JSON.parse`(문자열→객체)로 변환도 한 쌍이다. 이름과 실체가 어긋난 채 남은 것이다 — 다들 그냥 "Ajax"라고 부르지만 XML을 쓰는 경우는 이제 거의 없다.

## XHR에서 fetch로 — 문법이 비동기 모델을 따라왔다

도입의 XHR 코드가 낯선 이유는 **이벤트 기반**이기 때문이다. 요청을 보내두고, 응답이 오면 실행될 핸들러(`onload`)를 등록한다. 요청 하나면 견딜 만한데, "A를 받아서 그 결과로 B를 요청"하는 순간 핸들러 안에 핸들러가 중첩되기 시작한다.

그래서 ES6에서 프로미스가 표준이 되자, 프로미스를 반환하는 새 HTTP API가 나왔다. 그게 **fetch**다.

```javascript
const res = await fetch('/todos');
const todos = await res.json();
```

같은 일이 두 줄이 됐고, [HTTP 메시지 편](/network/05-http-message)에서 봤듯 옵션 객체가 요청 메시지의 구조(메서드·헤더·본문)와 그대로 대응한다. async/await, `Promise.all` 같은 비동기 조합 도구에도 자연스럽게 올라탄다.

다만 fetch에는 처음에 다들 한 번씩 걸려 넘어지는 함정이 있다. 직접 확인해봤다.

```javascript
const res = await fetch('https://example.com/no-such-page');
// 404인데도... rejected가 아니라 resolved
console.log(res.status, res.ok); // 404 false
```

**fetch는 404나 500에도 reject되지 않는다.** 서버가 응답을 줬다면 — 그 내용이 에러라도 — 통신 자체는 성공이라고 보기 때문이다. reject는 네트워크 단절, CORS 차단처럼 응답 자체를 못 받은 경우뿐이다. 그래서 `try/catch`만으로는 404가 잡히지 않고, `res.ok`(상태 코드가 2xx인지)를 직접 확인해야 한다. [상태 코드 편](/network/06-method-status)에서 "상태 코드는 기계가 먼저 읽는다"고 했는데, fetch는 그 판단을 개발자에게 넘기는 쪽을 택한 API인 셈이다.

## 이 전환이 만든 오늘의 프론트엔드

개인적으로 Ajax를 "옛날 기술"로 알고 넘어갔다가, 이게 지금 하는 개발의 전제 조건이라는 걸 뒤늦게 깨달았다. React로 만드는 SPA는 첫 HTML을 한 번 받은 뒤 **모든 서버 통신이 Ajax**다. 라우팅도 페이지를 새로 받는 게 아니라 자바스크립트가 화면을 갈아 끼우는 것이고, TanStack Query나 SWR 같은 라이브러리는 이 fetch 위에 캐싱과 재요청을 얹은 도구다. "페이지를 안 바꾸고 데이터만 받는다"는 20년 전의 발상이, 지금은 기본값이 된 것이다.

---

Ajax는 "서버 통신 = 페이지 전환"이라는 등식을 깬 사건이고, fetch는 그 통신을 프로미스라는 현대 비동기 모델의 언어로 다시 쓴 API다.

그런데 이렇게 데이터만 주고받게 되자 새로운 질문이 생긴다. 그 API의 주소와 메서드는 **어떤 약속으로** 설계해야 서로 헷갈리지 않을까. → [REST API는 무엇을 약속하나](/network/14-rest-api)
