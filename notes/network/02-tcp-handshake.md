# 연결은 왜 세 번 주고받으며 시작하나

[지난 글](/network/01-layered-model)에서 TCP가 데이터를 보내기 전에 "연결을 수립한다"고 했다. 그 수립 과정을 공부하다 만난 문제 하나.

```
클라이언트 → 서버: SYN, seq=3000
서버 → 클라이언트: SYN+ACK, seq=5000, ack=????
```

서버가 돌려주는 `ack` 번호는 몇일까?

나는 "3000번을 받았다"는 뜻으로 3000이라고 생각했는데, 답은 **3001**이다. ack는 "받은 번호"가 아니라 "**다음에 받기를 기대하는 번호**"다. 이 한 끗을 잡아두면 핸드셰이크부터 이후의 흐름 제어까지 ACK가 나오는 모든 장면이 한 번에 읽힌다.

## 연결 수립이라는 게 뭔가

물리적으로 보면 클라이언트와 서버 사이에 전용선이 깔리는 것도 아닌데, "연결됐다"는 건 무슨 상태일까. 사실 연결은 케이블 위가 아니라 **양쪽의 기억 속에** 만들어진다. 서로 "나는 이 번호부터 데이터를 보낼 것이고, 상대는 저 번호부터 보낼 것"이라는 합의를 기억하고, 각자 그 합의에 필요한 버퍼와 상태를 준비해 두는 것 — 그게 연결이다.

그 합의가 전화 통화의 시작과 닮았다. "여보세요, 들리세요?" / "네 들려요, 제 말은 들리세요?" / "네 잘 들립니다." 이 세 번의 주고받음이 **3-way 핸드셰이크**다.


숫자를 넣어 따라가 보자. 브라우저가 서버에 접속하며 초기 순서 번호(ISN)를 3000으로, 서버는 5000으로 정했다면:

1. 클라이언트 → 서버: `SYN, seq=3000` — "연결하자. 나는 3000번부터 보낼게"
2. 서버 → 클라이언트: `SYN+ACK, seq=5000, ack=3001` — "3001번을 기다릴게(3000번까지 받았다는 뜻). 나도 연결하자, 나는 5000번부터"
3. 클라이언트 → 서버: `ACK, ack=5001` — "5001번을 기다릴게"

이제 연결 수립(ESTABLISHED). 클라이언트가 보내는 첫 실제 데이터 — HTTPS 사이트라면 TLS ClientHello — 는 seq=3001부터 이어서 시작된다.

## 왜 두 번이 아니라 세 번인가

공부하면서 가장 먼저 들었던 의문이다. 서버가 SYN+ACK까지 보냈으면 서로 인사를 나눈 것 아닌가?

통신이 성립하려면 양쪽 모두 두 가지를 확인해야 한다. "**내 말이 상대에게 닿는다**"와 "**상대의 말이 나에게 닿는다**". 두 번째 SYN+ACK까지만 오간 시점을 보자.

- 클라이언트: 내 SYN에 응답이 왔으니 **내 말이 닿는 것 확인**, 상대의 SYN+ACK를 받았으니 **상대 말이 닿는 것도 확인**. 완료.
- 서버: 클라이언트의 SYN을 받았으니 상대 말이 닿는 건 확인했지만, **내 SYN+ACK가 클라이언트에게 닿았는지는 알 방법이 없다.**

세 번째 ACK가 도착해야 서버도 양방향을 확신하고 이 연결에 본격적인 리소스를 할당할 수 있다. 두 번이면 한쪽만 확신하는 반쪽짜리 합의가 된다.

초기 순서 번호를 0이 아니라 무작위 값에서 시작하는 데에도 이유가 있다. 이전 연결에서 지연되다 뒤늦게 도착한 세그먼트를 새 연결의 데이터로 착각하는 사고를 막고, 순서 번호를 추측해 남의 세션에 끼어드는 공격을 어렵게 만들기 위해서다.

그리고 이 왕복 한 번이 웹 성능 이야기와 바로 이어진다. HTTPS 첫 요청이 나가려면 TCP 핸드셰이크 1왕복이 **끝난 뒤에** TLS 핸드셰이크가 또 이어진다. 요청 한 번에 왕복이 겹겹이 쌓이는 이 구조가, 나중에 볼 [HTTP의 진화](/network/07-http-evolution)에서 QUIC이 태어난 배경이 된다.
